# Long File Splitter

## Overview

Finds source files in a repository that exceed a configurable line threshold (default **600 LoC**), works out **why each one grew that long**, and writes a per-file split proposal: concrete new module paths, what moves into each, and what to leave behind. Targets Python, JavaScript/TypeScript, HTML, and component-file formats (Vue, Svelte). Also detects files whose length is driven by a single large literal (a 700-line `CHOICES = {...}`, a 1200-line embedded HTML template string) and proposes extracting the data, not just rearranging the code.

This skill is **advisory by default**. The full proposal goes into a markdown report; the user reads it and decides what (if anything) to execute. An optional guided-execution phase will perform the moves, but only when the user explicitly asks for it, one file at a time, one commit per logical move, with the test suite run between commits.

## When to Use

- A codebase audit before a refactor sprint — "show me which files are the worst offenders"
- A specific complaint: "this `utils.py` is 1800 lines and I can't find anything in it"
- After a `python2-cleanup` or large pyupgrade pass that has visually inflated files
- Reviewing a legacy module before adding a feature — split first so the diff stays readable
- Picking the top-3 candidates to refactor this sprint without trying to fix everything
- Onboarding a new contributor — surface the modules that need archaeology

**Not for:**
- Auto-refactoring whole repos without human review. The proposal is the product, not the moves.
- Splitting files that are long but cohesive (a single test class with 60 focused tests, a Django migration auto-generated by the framework, a protobuf-generated client). The skill flags and **explicitly skips** these with a stated reason.
- Stylistic line-count enforcement. 600 LoC is a smell, not a sin — some files legitimately stay long (parsers, lexers, full state machines). The skill recommends; the user decides.
- Languages outside the supported set unless the user explicitly extends the glob list.

## Iron Laws

1. **Proposal before action.** Phase 1–4 read only. Nothing is moved, renamed, or deleted until the user explicitly says "execute the split for file X".
2. **No speculative refactors.** Touch only the file being split. Don't reformat the rest of the codebase, don't fix unrelated bugs noticed in passing, don't bump dependencies. Every diff line in the execution phase must be explainable as "part of splitting `<file>`".
3. **Preserve external API.** When splitting a file that other code imports from, the original module path **must keep working** — either by leaving a thin re-export shim or by updating every call site in the same commit. Pick one strategy per file and document it in the proposal.
4. **One file, one execution session.** Execute one oversized file at a time. Run the test suite after each split, commit, then move on. Never batch multiple file splits into a single commit.
5. **Skip honestly.** If a file is long for a legitimate reason (auto-generated, single cohesive unit, configuration file), the proposal says "SKIP — reason" rather than inventing a fake split.

## Phase 1: Repo Scan

The goal is a ranked list of candidate files. No analysis yet — just discovery.

### 1a. Pick the threshold and the file set

Default threshold: **600 LoC**. The user can override (e.g., "find files over 400 lines"). Default extensions:

```
.py .pyi
.js .jsx .mjs .cjs .ts .tsx
.html .htm
.vue .svelte
```

Default exclusions (don't even read these):

```
node_modules/  .venv/  venv/  env/  .env/  __pycache__/  .git/  .hg/
dist/  build/  out/  target/  .next/  .nuxt/  .cache/  .parcel-cache/
.tox/  .pytest_cache/  .mypy_cache/  .ruff_cache/  htmlcov/  coverage/
vendor/  third_party/  external/  bower_components/
*.min.js  *.min.css  *.bundle.js  *-lock.json  package-lock.json  yarn.lock
```

If the repo has unusual layout (e.g., vendored deps in `lib/`), confirm with `AskUserQuestion` before scanning.

### 1b. Run the discovery one-liner

```bash
THRESHOLD=600
rg --files \
   -g '*.{py,pyi,js,jsx,mjs,cjs,ts,tsx,html,htm,vue,svelte}' \
   --glob '!node_modules' --glob '!.venv' --glob '!venv' --glob '!env' \
   --glob '!__pycache__' --glob '!dist' --glob '!build' --glob '!out' \
   --glob '!target' --glob '!.next' --glob '!.nuxt' --glob '!.cache' \
   --glob '!.tox' --glob '!.pytest_cache' --glob '!.mypy_cache' \
   --glob '!.ruff_cache' --glob '!htmlcov' --glob '!coverage' \
   --glob '!vendor' --glob '!third_party' --glob '!external' \
   --glob '!bower_components' \
   --glob '!*.min.*' --glob '!*.bundle.js' \
| xargs wc -l 2>/dev/null \
| awk -v t="$THRESHOLD" '$1 >= t && $2 != "total"' \
| sort -rn
```

This prints lines + path, biggest first. Capture the output.

### 1c. Detect mega-constant files (Python)

Files can be **below** the LoC threshold yet still problematic because a single literal eats most of the file. Run a small AST pass over Python files to surface these:

```bash
python3 - <<'PY'
import ast, sys, pathlib, json
SPAN_THRESHOLD = 100  # lines a single literal must cover to be flagged
results = []
for path in pathlib.Path('.').rglob('*.py'):
    s = str(path)
    if any(skip in s for skip in ('/.venv/', '/venv/', '/__pycache__/',
                                  '/.git/', '/node_modules/', '/dist/',
                                  '/build/', '/.tox/', 'site-packages')):
        continue
    try:
        src = path.read_text(encoding='utf-8', errors='replace')
        tree = ast.parse(src)
    except (SyntaxError, OSError):
        continue
    total = src.count('\n') + 1
    for node in ast.iter_child_nodes(tree):
        if not isinstance(node, (ast.Assign, ast.AnnAssign)):
            continue
        end = getattr(node, 'end_lineno', node.lineno) or node.lineno
        span = end - node.lineno + 1
        if span < SPAN_THRESHOLD:
            continue
        tgt = node.targets[0] if isinstance(node, ast.Assign) else node.target
        name = tgt.id if isinstance(tgt, ast.Name) else '<?>'
        results.append({'path': s, 'name': name, 'start': node.lineno,
                        'end': end, 'span': span, 'file_lines': total,
                        'share': round(span / total, 2)})
results.sort(key=lambda r: r['span'], reverse=True)
for r in results:
    print(f"{r['path']}:{r['start']}-{r['end']}  {r['name']}  "
          f"({r['span']} lines, {int(r['share']*100)}% of file)")
PY
```

The output names every top-level Python assignment whose literal spans ≥100 lines, with its share of the file. A literal taking >50% of a 400-line file is a strong "extract this constant" signal even though the file is under the LoC threshold.

For JS/TS/HTML, equivalent literal detection is harder to do reliably without a real parser. The Phase-2 per-file reading step picks up these cases by inspection — note them there.

### 1d. Stamp each candidate as fresh or generated

Some long files are auto-generated and must not be touched. Detect the common cases by reading the first ~30 lines:

```bash
for f in $(rg --files -g '*.{py,js,ts}' | xargs wc -l 2>/dev/null \
           | awk '$1 >= 600 && $2 != "total" { print $2 }'); do
  head -30 "$f" | rg -l --no-messages -e 'Generated by Django' \
                                      -e 'DO NOT EDIT' \
                                      -e 'Generated by the protocol buffer compiler' \
                                      -e 'autogenerated by' \
                                      -e '@generated' \
                                      -e 'AUTOGENERATED' "$f" \
    && echo "  ^^^ GENERATED — skip"
done
```

Mark every generated file as `SKIP — generated` in the report. Migrations are a special case: Django migrations are technically generated but sometimes hand-edited; if a migration file is over 600 lines, the right move is usually to squash, not to split. Flag with that note.

### 1e. Produce the punch list

After the scan, before any per-file analysis, emit the punch list:

```
| Rank | File | Lines | Mega-const? | Generated? | Provisional category |
|-----:|------|------:|:-----------:|:----------:|----------------------|
|    1 | src/utils.py            | 1842 | no  | no | grab-bag |
|    2 | templates/dashboard.html| 1620 | n/a | no | many-sections |
|    3 | src/models/order.py     |  980 | yes (640L `STATUS_CHOICES`) | no | mega-constant |
|    4 | src/legacy/billing.py   |  870 | no  | no | god-class |
|    5 | migrations/0042_init.py |  720 | yes | yes (Django) | SKIP — generated |
```

Ask the user (via `AskUserQuestion`) which files to deep-dive on this pass. Default suggestion: the top 5 non-skipped. Skipping is fine and expected — long-file work is a marathon, not a sprint.

## Phase 2: Per-File Classification

For each file the user picked, read it end-to-end (or in chunks for very long files) and assign **one** category. Categories drive what the proposal looks like.

### Categories

**A. Grab-bag (utility module).**
Many small top-level units (≥10 functions or classes), each <80 lines, weakly related. Typical names: `utils.py`, `helpers.ts`, `common.js`, `misc.py`. Splits well by **domain**: strings, dates, http, fs, cache, etc.

**B. God-class / God-component.**
One or a few top-level units, each hundreds of lines. Typical: a 1000-line Django view class, a React component with 30 useState hooks, a 700-line ETL pipeline class. Splits by **responsibility within the unit** — extract helpers, mixins, sub-components.

**C. Mega-constant.**
A single literal (`dict`, `list`, multi-line `str`, JS array) takes ≥40% of the file. Typical: choice lists, ISO country tables, translation maps, embedded SQL, embedded HTML templates inside Python strings. Splits by **extracting the data** — move to a sibling `_data.py` / `_constants.py`, or to a `.json` / `.yaml` / `.toml` companion file when the data is pure (no callables, no imports).

**D. Many-section template (HTML).**
A large HTML file with clear visual or semantic sections (`<header>`, `<nav>`, repeated card markup, modals, `<footer>`). Splits via the template engine's include/partial/component mechanism.

**E. Mixed.**
Two of the above at once — e.g., a 1500-line `settings.py` that has both 30 small helper functions AND a 700-line `CHOICES` dict. Address both in the proposal, but in separate sub-sections.

**F. SKIP — cohesive.**
Long but justifiably so. A single tokenizer, a complete state machine, a generated client, a snapshot test fixture, a hand-tuned regex bank. Note the reason and move on.

### How to decide quickly

Tools that help, in order of cheapness:

1. **Python AST summary** (free, fast):

   ```bash
   python3 - <<'PY' path/to/file.py
   import ast, sys
   tree = ast.parse(open(sys.argv[1]).read())
   funcs, classes, assigns_big = [], [], []
   for n in ast.iter_child_nodes(tree):
       end = getattr(n, 'end_lineno', n.lineno) or n.lineno
       span = end - n.lineno + 1
       if isinstance(n, ast.FunctionDef):
           funcs.append((n.name, span))
       elif isinstance(n, ast.AsyncFunctionDef):
           funcs.append(('async ' + n.name, span))
       elif isinstance(n, ast.ClassDef):
           classes.append((n.name, span))
       elif isinstance(n, (ast.Assign, ast.AnnAssign)) and span >= 50:
           tgt = n.targets[0] if isinstance(n, ast.Assign) else n.target
           assigns_big.append((tgt.id if isinstance(tgt, ast.Name) else '<?>', span))
   print(f"functions: {len(funcs)} (avg span "
         f"{sum(s for _,s in funcs)//max(1,len(funcs))})")
   print(f"classes:   {len(classes)}")
   for c, s in classes: print(f"  - {c}  ({s} lines)")
   print(f"big literals (≥50L):")
   for n, s in assigns_big: print(f"  - {n}  ({s} lines)")
   PY
   ```

2. **JS/TS top-level survey**: `rg -n '^(export\s+)?(async\s+)?(function|class|const|let|var)\s+\w+' path/to/file.ts | head -50` gives a sense of the unit count and naming patterns. React components often look like `export function Foo(...)` followed by 200 lines of JSX.

3. **HTML section survey**: `rg -n '^\s*<(section|header|nav|footer|main|article|aside|div\s+class="[^"]*(?:section|panel|card|modal)[^"]*")\b' path/to/file.html` reveals the structural skeleton.

4. **Read the file directly** when the heuristics are ambiguous. Don't trust counts alone — naming patterns and import structure usually decide between "grab-bag" and "god-module".

Record the category and the structural summary in the proposal entry.

## Phase 3: Cohesion Analysis

Before proposing names, work out **what groups with what**. The proposal is only as good as the grouping.

### For Python grab-bag modules

Signals to use, roughly in order:

- **Name prefix / suffix clusters.** `parse_*`, `format_*`, `slugify_*` → text. `to_local`, `parse_iso`, `now_utc` → dates. `safe_*` paired with `os.*` → fs.
- **Import affinity.** Functions that share third-party imports cluster: only the http-ish functions touch `httpx`, only the date ones touch `zoneinfo`. Group by which functions reach for which imports.
- **Data type signatures.** If a function takes/returns `datetime`, it's a date helper; `bytes` → binary/fs; `httpx.Response` → http.
- **Callers.** `rg -l 'from utils import slugify'` shows who uses what — if call sites cluster by feature, that's a clue (e.g., all `slugify` calls are in the blog app; consider moving it there).
- **Existing comments / section headers.** Long files often have `# === DATE HELPERS ===` style banners. Trust them as the first draft of the split.

### For god-classes / god-components

- **Method clusters by lifecycle.** `__init__` / `setup` / `load_*` → init phase. `run` / `process` / `step` → main loop. `cleanup` / `teardown` / `close` → finalization. Each phase can become a helper module or mixin.
- **Method clusters by data.** Methods touching only `self._cache` cluster; methods touching only `self._db` cluster. Pull each cluster into a focused collaborator.
- **Hooks vs core logic.** Django views often mix `get_queryset` / `get_context_data` / `get_form_kwargs` (framework hooks) with custom business methods. Hooks stay; business methods can move to a service object.
- **React/Vue components.** Group hooks into custom hooks. Pull JSX subtrees with their own state into subcomponents. Move pure helpers above the component to a sibling file.

### For mega-constants

- **Is the data pure?** No callables, no imports, no f-strings, no `lambda` — yes, pure. Pure data should live in `.json` / `.yaml` / `.toml`, not Python.
- **Is the data used by more than one module?** Yes → extract to a shared `_data.py` and import. No → extract to a sibling `_constants.py` next to the consumer.
- **Is the data conceptually layered?** A 700-line `CHOICES` dict might decompose into `PAYMENT_CHOICES`, `USER_CHOICES`, `ORDER_CHOICES` — propose the split with the dict.

### For HTML templates

- **Repetition.** If `<div class="card">…</div>` appears 14 times, the template wants a loop and a partial.
- **Cross-page reuse.** A nav block likely repeats in 3 templates. Extract once, include thrice.
- **Engine fit.** Django → `{% include %}` + `templatetags`. Jinja → `{% include %}` / `{% import %}`. React/Vue/Svelte → subcomponents. The split target follows the project's engine.

## Phase 4: Proposal Output

Emit a single markdown report. Default path:

```
/tmp/long-file-split-proposal-<YYYY-MM-DD-HHMMSS>.md
```

Use this exact template:

```markdown
# Long file split proposal — <repo name>

**Threshold:** <N> LoC
**Scan date:** <ISO timestamp>
**Files scanned:** <count>
**Candidates found:** <count> (of which <K> skipped)

## Punch list

<table from Phase 1e>

## Per-file proposals

### `<relative/path/to/file.py>` — <N> lines  ·  Category: <A–F>

**Structural summary.** <one paragraph: top-level units, biggest unit, big literals, key imports>

**Why it grew.** <one paragraph: archaeological guess — accretion of helpers / single class that absorbed responsibilities / data shipped inline that should have been a config file / repeated layout never extracted>

**Cohesion analysis.** <bullet list: name clusters, import affinity, lifecycle groups, etc.>

**Proposed split.**

| New file | Symbols moved | Approx. lines | Rationale |
|----------|---------------|--------------:|-----------|
| `<path>` | `funcA`, `ClassB`, `CONST_C` | ~<N> | <one sentence why these belong together> |
| `<path>` | ... | ... | ... |
| `<original>` | <what stays — typically re-exports or the "core" public API> | ~<N> | <why this layer stays> |

**Public API preservation.** <one of: "Original path keeps working via re-export shim" / "All call sites updated in the same commit" / "Both — call sites updated AND shim retained for 1 release with `DeprecationWarning`">

**Risks.**
- <risk>: <mitigation>
- ...

**Suggested commit sequence.**
1. <step>
2. <step>
3. ...

**SKIP reason** (if category F): <one sentence>

---

### `<next file>` — ...
```

Notes on writing the proposal:

- **Be concrete.** "Move date helpers to `utils/dates.py`" is useless without naming them. Always list the symbols by name.
- **Estimate, don't guess.** Use AST spans to estimate per-new-module line counts; don't make numbers up.
- **One paragraph per section.** This report gets read end-to-end; a wall of text fails its job.
- **State the trade-off when there is one.** If the cleanest split would create a circular import, say so and propose a structure that avoids it (often: move shared types to `_types.py`).
- **Suggest a minimum viable split.** A 1800-line file does not have to become 12 modules. If the cleanest improvement is `original.py` (1100 lines) + `original/_data.py` (700 lines), that's the proposal — don't over-engineer.

After the report is written, tell the user the path and ask (via `AskUserQuestion`) whether to (a) stop here, (b) iterate on a specific proposal, or (c) execute one of the splits.

## Phase 5 (optional): Guided Execution

Only enter this phase when the user explicitly says "execute the split for `<file>`" (or equivalent). Even then, do **one** file at a time, with these steps:

### 5a. Pre-flight

1. **Working tree clean.** `git status` must show no uncommitted changes. If dirty, refuse and ask the user to commit or stash. Splits create complex diffs; mixing them with unrelated work makes review impossible.
2. **Tests green.** Run the project's test command (`uv run pytest`, `npm test`, `make test`, whatever the project uses). If red, refuse — you need a green baseline to detect regressions caused by the split.
3. **Branch.** Suggest a branch named `split/<original-stem>` and create it if the user agrees.

### 5b. Apply, commit, test — per logical move

For each row in the proposal's "Proposed split" table:

1. Create the new file. Move the symbols. Leave behind a re-export in the original path **or** update every call site — whichever the proposal specified.
2. Run the test suite. **If it goes red, revert this commit and stop.** Report what failed; don't try to fix it inside the split flow.
3. Commit with a focused message:

   ```
   refactor(<scope>): extract <what> from <original>

   Moved <N> symbols (<names>) to <new path>.
   <original> now re-exports them for backwards compatibility.

   Part of splitting <original> (proposal: /tmp/long-file-split-proposal-…).
   ```

4. Move to the next row.

### 5c. Final pass

After every row in the proposal has its commit, run the full test suite once more. Optionally run static checks (`ruff check`, `mypy`, `tsc --noEmit`, `eslint`) and fix any new warnings the split introduced — but only those directly caused by the split (e.g., a missing `__all__`, an unused import). Don't reach beyond.

### 5d. Re-exports lifecycle

If you left re-export shims, also produce a short follow-up note in the proposal: which shims should be deprecated and when. A reasonable pattern is "shim stays for 1 release with a `DeprecationWarning`, removed in the release after". Don't add the deprecation warning silently — propose, let the user decide.

## Per-language quick reference

### Python

- **Re-export shim:** in the original file, `from .new_module import a, b, c` plus `__all__ = [...]`. Existing `from old_module import X` keeps working unchanged.
- **Mega-constants → pure data:** if the literal is a `dict[str, str]` / `list[str]` / `dict[str, list[str]]` with no callables, prefer `.json`. Read once at import time with `json.loads((Path(__file__).parent / "data.json").read_text())`. Keep type annotations in the Python wrapper.
- **God-class split:** prefer composition over inheritance/mixins. A `Foo` class with a `_db` collaborator and a `_cache` collaborator is easier to test than a `Foo(DbMixin, CacheMixin)`.
- **Django specifics:**
  - `views.py` → `views/__init__.py` + `views/users.py` + `views/orders.py`. Keep URLConf imports stable.
  - `models.py` → `models/__init__.py` re-exporting all models. `Meta.app_label` must be set on each model when models live in subpackages.
  - `admin.py` → split by app section, each registering its own models.
  - `serializers.py` (DRF) → split per resource.

### JavaScript / TypeScript

- **Barrel files (`index.ts`):** the equivalent of a re-export shim. Original consumers `import { X } from 'utils'` keep working.
- **Component split:** colocate subcomponents in a folder. `Dashboard.tsx` → `Dashboard/index.tsx` + `Dashboard/Header.tsx` + `Dashboard/Card.tsx` + `Dashboard/useDashboardData.ts`.
- **Hook extraction:** every `useState`/`useEffect` cluster with a clear purpose can become a custom hook in `hooks/useFoo.ts`.
- **Types split:** if a 600-line `types.ts` is mostly unrelated types, split per domain — but keep the barrel.
- **Avoid:** turning a 1-file 800-line module into 20 trivial files. Tooling overhead (imports, paths) eats the win.

### HTML / templates

- **Django:** `{% include "myapp/_card.html" with item=x %}` for partials; custom template tags for repeated logic.
- **Jinja:** same `{% include %}` mechanism; `{% import %}` for macros.
- **React/Vue/Svelte:** every visually distinct region with its own state or props becomes a component file.
- **Externalize embedded CSS/JS:** a `<style>` or `<script>` block over ~50 lines inside an HTML file should move to a separate `.css` / `.js` file referenced by `<link>` / `<script src>`.

## Common mistakes to avoid

- **Splitting on length alone.** A 700-line file with one tightly-coupled state machine should stay one file. The threshold is a flag, not a verdict.
- **Premature multiplication.** Don't propose 8 new files when 2 would do. Each new file has overhead — imports, navigation, mental load.
- **Breaking API silently.** Moving `slugify` out of `utils.py` without keeping `from utils import slugify` working will break callers in other repos that depend on this package. Always state the API-preservation strategy.
- **Mixing categories per move.** A single commit must address one logical concern — "extract date helpers" OR "extract big constant", not both.
- **Ignoring circular imports.** When two new modules need each other, the proposal must point that out and suggest a `_types.py` / `_interfaces.py` to break the cycle.
- **Refactoring "while you're there".** Don't rename functions, change signatures, or fix bugs during a split. Splits are a layout change; behavior must be identical.
- **Skipping the test run.** "It should be fine" is how a clean split becomes a Friday-evening bisect. Tests run after every commit, no exceptions.

## Workflow summary

```
Phase 1 — Scan
    ├─ 1a. Threshold + extension set
    ├─ 1b. rg + wc + awk → ranked list
    ├─ 1c. AST pass for Python mega-constants
    ├─ 1d. Generated-file detection (skip)
    └─ 1e. Punch list + AskUserQuestion: which files this pass?

Phase 2 — Classify each picked file
    └─ Category A (grab-bag) / B (god-class) / C (mega-constant)
       / D (HTML many-section) / E (mixed) / F (skip — cohesive)

Phase 3 — Cohesion analysis
    └─ Name clusters, import affinity, lifecycle groups, repetition

Phase 4 — Proposal
    └─ /tmp/long-file-split-proposal-<ts>.md
       (punch list + per-file: structure / why / split table / risks / commit plan)

Phase 5 — (opt-in) Guided execution, ONE file
    ├─ 5a. Pre-flight: clean tree, green tests, branch
    ├─ 5b. Per row: move → test → commit
    ├─ 5c. Final pass + light static checks
    └─ 5d. Re-export lifecycle note
```

The product of this skill is the **proposal**. Execution is a bonus path the user can opt into, file by file. Treat the proposal as the deliverable and write it like a document that someone six months from now will use to decide whether the refactor is worth doing.
